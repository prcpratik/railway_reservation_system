Abstract

RailSathi is a full-stack, AI-powered railway reservation system designed and developed as the capstone project for the CDAC PG-CP AC program. The system replicates core functionalities of India's railway booking infrastructure — including train search with intermediate stations, multi-class seat management, dynamic fare calculation based on distance, real-time seat availability, waitlist management with automatic promotion, Razorpay-integrated payment processing, and email notifications — while augmenting it with a Generative AI chatbot powered by the Groq LLM (LLaMA 3.3 70B) for natural-language train enquiries.

The architecture follows a microservices-oriented pattern with four independently deployable components: a React 18 frontend (Vite), a Spring Boot 3.5 REST backend, a FastAPI GenAI service, and a Node.js Express API gateway that unifies routing and cross-origin concerns. Data persistence is handled by MySQL 8 via Spring Data JPA with Hibernate ORM. Security is implemented through JWT-based stateless authentication with BCrypt password hashing and role-based access control (RBAC).

Key engineering highlights include pessimistic database locking to prevent seat overselling under concurrent bookings, HMAC-SHA256 payment signature verification, AOP-based cross-cutting logging, and a comprehensive DTO layer to decouple the API contract from the persistence model.

Keywords: Railway Reservation, Full-Stack, Spring Boot, React, GenAI, LLM, Razorpay, JWT, Microservices, CDAC

Chapter 1: Introduction

1.1 Background

The Indian Railways is the fourth-largest railway network in the world, carrying over 8 billion passengers annually. The existing online reservation system (IRCTC) handles millions of concurrent transactions, making railway ticketing one of the most demanding real-time systems in the country. Understanding the engineering behind such a system — from concurrent seat management to secure payment processing — provides an excellent learning opportunity for advanced computing students.

1.2 Motivation

The motivation for RailSathi stems from the desire to build a production-grade, full-stack application that covers the core CDAC PG-CP AC syllabus topics (Spring Boot, React, MySQL, Spring Security, AOP, Redux) within a single, cohesive project rather than disconnected lab exercises. By choosing the railway reservation domain, the team addresses real-world challenges such as:

  • Concurrent access and data integrity (multiple users booking the last seat simultaneously)
  • Multi-entity relational data modelling (trains → classes → stops → bookings → passengers)
  • Secure, stateless authentication across a decoupled frontend and backend
  • Third-party integration (Razorpay payments, Gmail SMTP, Groq LLM)

1.3 Scope

RailSathi is designed as a web-based railway reservation platform offering:

  • User registration and login with JWT-based security
  • Train search with intermediate-station routing and day-of-week filtering
  • Multi-class, distance-proportional fare booking for up to 6 passengers per ticket
  • Waitlist management with automatic seat promotion on cancellation
  • Razorpay test-mode online payment with HMAC signature verification
  • Full and partial cancellation with automated refunds
  • Email notifications (booking confirmation and cancellation)
  • AI-powered chatbot for train enquiries using Groq LLM
  • Admin dashboard for train management, booking oversight, and admin creation

1.4 Project Overview

The system follows a four-service architecture:

  1. Frontend — React 18 SPA served by Vite dev server (port 5173)
  2. API Gateway — Node.js Express reverse proxy (port 8080) routing /api/genai/* to the GenAI service and /api/* to Spring Boot
  3. Backend — Spring Boot 3.5 REST API (port 8081) with Spring Data JPA + MySQL
  4. GenAI Service — Python FastAPI (port 8083) integrating Groq's LLaMA 3.3 70B model via LangChain

Chapter 2: Problem Statement & Objectives

2.1 Problem Statement

Design and implement a full-stack, AI-enhanced railway reservation system that allows passengers to search trains, book and cancel tickets with real-time seat availability, process online payments securely, receive email notifications, and interact with an intelligent chatbot — while administrators manage trains and monitor all bookings through a dedicated dashboard.

2.2 Objectives

  1. To build a secure, role-based web application with JWT authentication and BCrypt password hashing.
  2. To implement concurrency-safe seat booking using pessimistic database locking to prevent double-selling.
  3. To support intermediate-station routing and distance-based proportional fare calculation.
  4. To integrate Razorpay payment gateway (test mode) with server-side HMAC-SHA256 signature verification.
  5. To provide waitlist management with automatic promotion when seats become available.
  6. To offer full and partial ticket cancellation with automated refund processing.
  7. To send email notifications on booking confirmation, cancellation, and waitlist promotion.
  8. To integrate a Generative AI chatbot using Groq LLM for natural-language train enquiries.
  9. To implement the complete CDAC syllabus topics (Spring Boot, React, Redux, JPA, AOP, Security) in a cohesive application.
  10. To maintain clean architecture with proper layering (Controller → Service → Repository), DTOs, and separation of concerns.

Chapter 12: Implementation Details

12.1 Concurrency Control — Pessimistic Locking

The most critical engineering challenge is preventing two users from booking the last available seat simultaneously. RailSathi solves this with a pessimistic write lock:

// TrainRepository.java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT t FROM Train t WHERE t.id = :id")
Optional<Train> findByIdForUpdate(@Param("id") Long id);

At the start of BookingService.book(), the train row is locked with SELECT ... FOR UPDATE. Since the method is @Transactional, the lock is held until the transaction commits. A concurrent booking for the same train blocks on the lock, then re-counts seats and correctly sees the updated availability. Bookings for different trains lock different rows, so they proceed in parallel.

12.2 Seat Availability — Computed, Not Stored

available = classCapacity - COUNT(CONFIRMED passengers on train+class+date)

This approach ensures that cancellations (even partial) automatically free seats without maintaining a counter. The database is always the source of truth.

12.3 Part-Journey Fare Calculation

segmentFare = classFare × (toKm − fromKm) / (lastStopKm − firstStopKm)

The fareShare() method on the Train entity computes the proportional fare using the distanceFromSource values from the TrainStop entities. This is used both for displaying fares in search results and for locking the fare at booking time.

12.4 Payment Security — HMAC-SHA256 Verification

The Razorpay checkout runs entirely in the browser. To prevent a tampered frontend from faking a payment:

  1. Backend creates a Razorpay order (server-to-server with the secret key)
  2. Frontend opens the Razorpay popup, collects payment
  3. Razorpay signs orderId|paymentId with the secret key (HMAC-SHA256)
  4. Frontend sends paymentId + signature to /api/bookings/{id}/pay
  5. Backend recomputes the signature with its copy of the secret key
  6. Only if signatures match is the booking marked CONFIRMED

12.5 Waitlist Promotion Algorithm

  1. When a seat is freed (cancellation), promoteFromWaitlist() is called
  2. Fetch the waitlist queue ordered by waitlistNumber ASC
  3. For each freed seat, promote the earliest waiting passenger:
    • Change status from WAITLISTED → CONFIRMED
    • Assign the freed seat number
    • Clear waitlistNumber
  4. Renumber remaining waitlisted passengers (WL3 → WL2, etc.)
  5. Send promotion email to each promoted passenger's booking user
  6. Recompute the booking status of all affected bookings

12.6 Email Enumeration Prevention

The forgot-password endpoint returns the same message ("If that email is registered, a reset link has been sent") for both registered and unregistered emails. This prevents attackers from scripting address enumeration. The same principle applies to login ("Invalid email or password" — not distinguishing which is wrong).

12.7 DTO Pattern

Controllers return BookingResponse / PassengerResponse record DTOs instead of raw JPA entities. Benefits:

  • API shape is explicit and decoupled from the database schema
  • Prevents leaking nested entities (e.g., User inside Booking) into JSON
  • Avoids lazy-loading / infinite recursion issues during serialization
  • Java records are immutable and concise

12.8 Redux State Management

Redux is used only for authentication state (logged-in user), which is needed by multiple components (Navbar, route guards, booking page). Page-local data (train search results, form fields) uses React's useState — avoiding unnecessary Redux boilerplate.

Chapter 15: Conclusion

RailSathi successfully demonstrates the design and implementation of a production-grade, AI-enhanced railway reservation system that integrates all core technologies covered in the CDAC PG-CP AC curriculum.

Through this project, the team gained hands-on experience with:

  • Full-stack development — building a decoupled React frontend communicating with a Spring Boot REST API through a Node.js API gateway
  • Relational database modelling — designing a normalised schema with complex relationships (trains → classes → stops → bookings → passengers)
  • Security engineering — implementing JWT-based stateless authentication, BCrypt password hashing, role-based access control, and HMAC payment verification
  • Concurrency control — using pessimistic database locking to prevent data integrity issues in high-contention scenarios
  • Third-party integration — integrating Razorpay for payments, Gmail SMTP for notifications, and Groq LLM for AI-powered chat
  • Software engineering practices — clean layered architecture, DTO pattern, AOP cross-cutting concerns, comprehensive testing with Mockito and concurrency tests
  • AI/ML integration — connecting a large language model to live application data through a context-aware prompt engineering approach

The system handles real-world complexity including intermediate-station routing, distance-proportional fare calculation, waitlist management with automatic promotion, partial cancellation with proportional refunds, and email enumeration prevention — going well beyond a basic CRUD application.

RailSathi serves as a strong foundation that can be extended with features like segment-based availability, Tatkal booking, live tracking, and containerised deployment to approach production readiness.
